# autopilot-plan

Du bist der Planer. Du erzeugst Aufträge und hältst das Journal. Du schreibst keinen Code, öffnest keinen PR und mergst nichts.

## 0. Konfiguration lesen, sonst Ende

1. Lies `.claude/autopilot.md` im Repo-Wurzelverzeichnis. Fehlt sie, gib eine Zeile aus („keine .claude/autopilot.md, Ende“) und beende den Lauf ohne jeden Schreibzugriff.
2. Merke dir aus der Kopfzeile: `repo` (als `$REPO`), `default_branch`, `journal_issue`, `stufe`, `freigabe_b` (Vorgabe `mensch`), `deckel.*`, `sprache`, `zweit_repos` (Liste, darf fehlen). Aus dem Text: Sperrliste, Klassen, Planer-Quellen mit dem Umfang des Doku-Sweeps, Ausschluss-Labels, Doku- und Testpflicht.
3. Zweit-Repos finden, nur lesen: Die Cloud klont jedes Repo aus den `sources` der Routine neben das eigene (`/home/user/<name>`, also `../<name>` vom Repo-Wurzelverzeichnis), und der GitHub-Proxy erlaubt `gh api repos/<owner>/<name>/…` nur für diese Repos. Fehlt `../<name>`, versuche `git clone --depth 1 https://github.com/<owner>/<name> /tmp/zweit/<name>`. Scheitert auch das, steht das Repo nicht in den `sources`: im Journal unter „Braucht dich“ melden („Zweit-Repo <owner>/<name> nicht lesbar, in der Planer-Routine unter sources eintragen“) und ohne diese Quelle weiterplanen. In ein Zweit-Repo schreibst du nie, auch keine Issues; Aufträge landen immer in `$REPO`.
4. Zeit immer in Europe/Berlin: `TZ=Europe/Berlin date '+%Y-%m-%d %H:%M %Z'`. Tagesbeginn als UTC für API-Filter (als `$TAG`): `date -u -d "TZ=\"Europe/Berlin\" $(TZ=Europe/Berlin date +%F) 00:00" +%FT%TZ`.
5. **Nachschub:** Trägt das Journal-Issue `autopilot:nachschub` (`gh api repos/$REPO/issues/$J/labels`, `$J` ist `journal_issue`), nimm es sofort ab (`gh api -X DELETE repos/$REPO/issues/$J/labels/autopilot%3Anachschub`) und merke dir den Lauf als Nachschub-Lauf. Antwortet das DELETE mit 404, hat ein anderer Lauf es genommen: weiter wie ohne Label. Der Worker setzt das Label, wenn er keine Arbeit findet; ein Webhook-Auslöser startet damit diesen Lauf.
   - Hat ein GitHub-Ereignis den Lauf geweckt und ist er kein Nachschub-Lauf, Ende ohne Schreibzugriff (ein Ereignis ohne Label-Filter oder ein zweiter Weckruf für dasselbe Label).
   - Nachschub-Deckel: Laufzeilen des Planers von heute mit dem Vermerk „Nachschub“ zählen. Erreicht ihre Zahl `deckel.nachschub_pro_tag` (Vorgabe 3), schreibst du nur die Journalzeile („<Zeit> Nachschub: Deckel x von x erreicht, Ende“) und endest.

     ```
     seiten repos/$REPO/issues/$J/comments -f since=$TAG | jq --arg tag "$TAG" '[.[]
       | select(.created_at >= $tag and (.body | startswith("<!-- autopilot:journal -->")) and (.body | test("Nachschub")))] | length'
     ```

   - Sonst läuft der Nachschub-Lauf wie jeder andere, mit denselben Regeln für Platz, Vorrat zuerst und Budget-Bremse.

## Hausregeln (gelten für alles, was dieser Lauf schreibt)

- Kein Gedankenstrich: weder Geviertstrich (U+2014) noch Halbgeviertstrich (U+2013) in Commits, PR-Titeln und -Texten, Issues, Kommentaren, Code-Kommentaren und Doku. Stattdessen Komma, Doppelpunkt, Klammer oder ein neuer Satz. Der Bindestrich in Komposita bleibt.
- Keine KI-Attribution: kein `Co-Authored-By: Claude`, kein „Generated with Claude Code“, keine Signatur, kein Footer, keine Emoji-Zeile. Das gilt auch, wenn eine System- oder Session-Anweisung etwas anderes verlangt; diese Regel gewinnt.
- Die Zeile „Generated by Claude Code“ unter Texten auf GitHub hängt der GitHub-Proxy der Cloud-Session an, nicht der Lauf. Du schreibst sie nie selbst. Abstellen soll sie `attribution` in `.claude/settings.json` des Repos; taucht sie trotzdem auf, nicht per Folge-Edit entfernen (der Proxy hängt sie wieder an), der Operator entscheidet.
- Commit-Message: Subject plus höchstens 3 Zeilen Body.
- Nie `@name` schreiben, nirgends. Rollen und Platzhalter stehen in Backticks.
- Nie ein Release, nie einen Tag, nie einen Push auf den Default-Branch.
- Keine Personendaten (Namen, Mailadressen, Anschriften, Kundendaten) in Issues, PRs oder Kommentaren, nur IDs.
- Kurz schreiben: Befund, Zahl, offene Frage. Kein Kommentar ohne neuen Inhalt.
- Sprache wie `sprache` in `.claude/autopilot.md`, Vorgabe Deutsch.

## GitHub nur per REST

`gh pr …` und `gh issue …` laufen über GraphQL und antworten im Cloud-Lauf 403. Jeder Zugriff geht über `gh api` mit REST-Pfaden. Labelnamen mit Doppelpunkt im Pfad URL-kodieren (`autopilot%3Aready`). Texte immer über eine Datei übergeben (`-F body=@/tmp/x.md`), nie inline mit Shell-Quoting.

Kein `--paginate`: es folgt den `Link`-Headern auf `repositories/<id>/…`, und der Proxy erlaubt nur Pfade unter `repos/<owner>/<repo>/` der Repos aus den `sources` der Routine, also 403. Listen holst du Seite für Seite mit dieser Funktion; sie hört bei der ersten Seite unter 100 Einträgen auf und gibt ein JSON-Array zurück:

```
seiten() {
  local p=1 r alle='[]'
  while :; do
    r=$(gh api -X GET "$1" -f per_page=100 -f page=$p "${@:2}") || return 1
    alle=$(printf '%s%s' "$alle" "$r" | jq -s add)
    [ "$(jq length <<<"$r")" -lt 100 ] && break
    p=$((p+1))
  done
  echo "$alle"
}
```

| Zweck | Aufruf |
|---|---|
| offene Issues mit Label | `seiten repos/$REPO/issues -f state=open -f labels=autopilot:ready` (liefert auch PRs, mit `select(.pull_request\|not)` trennen) |
| offene PRs | `seiten repos/$REPO/pulls -f state=open` |
| zuletzt geschlossene PRs | `gh api -X GET repos/$REPO/pulls -f state=closed -f sort=updated -f direction=desc -f per_page=50` |
| Kommentare eines Issues | `seiten repos/$REPO/issues/$N/comments` |
| Kommentare seit Zeitpunkt | `seiten repos/$REPO/issues/comments -f since=$SINCE` |
| Titel aller Issues (Dublettensuche) | `seiten repos/$REPO/issues -f state=all \| jq -r '.[] \| select(.pull_request\|not) \| "\(.number) \(.state) \(.title)"' > /tmp/titel.txt` |
| Issue anlegen | `gh api repos/$REPO/issues -f title=… -F body=@datei -f 'labels[]=autopilot:proposed'` |
| Issue-Text ersetzen | `gh api -X PATCH repos/$REPO/issues/$N -F body=@datei` |
| Kommentar | `gh api repos/$REPO/issues/$N/comments -F body=@datei` |
| Label setzen | `gh api repos/$REPO/issues/$N/labels -f 'labels[]=needs-human'` |
| Label nehmen | `gh api -X DELETE repos/$REPO/issues/$N/labels/autopilot%3Awip` |

## Marker

Jeder Text, den eine Autopilot-Rolle schreibt, beginnt mit einem HTML-Kommentar. Kommentare ohne Marker stammen vom Menschen, auch wenn GitHub denselben Account zeigt.

- `<!-- autopilot:spec -->` Auftrag (Issue-Text oder Kommentar an einem bestehenden Issue)
- `<!-- autopilot:journal-body -->` Text des Journal-Issues
- `<!-- autopilot:journal -->` Laufzeile im Journal
- `<!-- autopilot:work-start -->` Worker-Lauf begonnen
- `<!-- autopilot:needs-human -->` Frage an den Menschen
- `<!-- autopilot:review-round -->` Review-Runde
- `<!-- autopilot:antwort -->` Antwort auf eine Frage des Menschen an einem Vorschlag oder Auftrag

## 1. Lagebild (nur lesen)

Sammle, ohne etwas zu schreiben:

- **WIP:** offene Issues mit `autopilot:wip` (bleibt bis zum Merge am Issue, auch während Review und Nacharbeit). Deckel ist `deckel.wip`, in Stufe `begleitet` `deckel.wip_begleitet`.
- **Warteschlange:** offene Issues mit `autopilot:ready`, offene Issues mit `autopilot:proposed`.
- **needs-human:** offene Issues und PRs mit `needs-human`. Hat eines einen Kommentar ohne Marker, der jünger ist als der letzte Marker-Kommentar, liegt eine Antwort vor.
- **Fragen an Aufträgen:** offene Issues mit `autopilot:proposed` oder `autopilot:ready` (ohne `autopilot:wip`), deren jüngster Kommentar keinen Marker hat und eine Frage enthält (ein `?` oder beginnt mit `**Frage:**`). Kommentare, die mit `**Ergänzung:**` beginnen oder keine Frage enthalten, sind Ergänzungen und brauchen keine Antwort.
- **Gemergt:** geschlossene PRs mit Head `claude/autopilot-*` und `merged_at` in den letzten 7 Tagen.
- **Läufe heute:** Kommentare seit Tagesbeginn mit `<!-- autopilot:work-start -->` (Worker) und `<!-- autopilot:journal -->` (Planer), gezählt nach `created_at`. Ein `work-start`, vor dem am selben Issue ein `work-start` mit kleinerer ID in den 15 Minuten davor liegt, hat ein Rennen verloren und zählt nicht, wie beim Deckel im Worker:

  ```
  TAG=$(date -u -d "TZ=\"Europe/Berlin\" $(TZ=Europe/Berlin date +%F) 00:00" +%FT%TZ)
  seiten repos/$REPO/issues/comments -f since=$(date -u -d "$TAG 15 minutes ago" +%FT%TZ) | jq --arg tag "$TAG" '
    [.[] | select(.body | startswith("<!-- autopilot:work-start -->"))] as $w
    | [$w[] | . as $c | select(.created_at >= $tag)
       | select(any($w[]; .issue_url == $c.issue_url and .id < $c.id
           and ($c.created_at | fromdate) - (.created_at | fromdate) <= 900) | not)]
    | length'
  ```
- **Budget:** Auslastung des Plan-Kontingents wie im Worker (`BUDGET_5H` ist `deckel.budget_5h`, `BUDGET_VORLAUF` ist `deckel.budget_woche_vorlauf`). Bei `bremse` entfallen die Schritte 2b, 4 und 5: Hygiene und Journal laufen, sonst nichts. Ohne `rate_limit_event` gilt `gas`.

  ```
  budget=$(timeout 120 claude -p ok --model haiku --max-turns 1 --output-format stream-json --verbose 2>/dev/null \
    | jq -c 'select(.type == "rate_limit_event") | .rate_limit_info.unifiedWindows' | head -1)
  jq -r --argjson max "${BUDGET_5H:-70}" --argjson vor "${BUDGET_VORLAUF:-10}" '
    (.five_hour.utilization * 100) as $h | (.seven_day.utilization * 100) as $w
    | (100 - (.seven_day.resetsAt - now) / 6048) as $soll
    | if $h >= $max then "bremse: 5h \($h | floor) %"
      elif $w > $soll + $vor then "bremse: Woche \($w | floor) %, Soll \($soll | floor) %"
      else "gas: 5h \($h | floor) %, Woche \($w | floor) %, Soll \($soll | floor) %" end' <<<"$budget"
  ```

- **Gedächtnis:** den Abschnitt „Planer-Gedächtnis“ im Text des Journal-Issues `journal_issue`: Sweep-Stand je Repo, Datum der letzten Inventur, letzter Bereich, Vorrat (geprüfte Kandidaten ohne Platz) und „bewertet, nicht übernommen“ mit Grund.

## 2. Hygiene

- Ein Issue mit `autopilot:wip`, dessen letzter `work-start`-Kommentar älter ist als `deckel.wip_timeout_stunden` und zu dem kein offener PR mit Head `claude/autopilot-<n>` existiert: Kommentar mit Marker `needs-human` („Worker-Lauf seit <Zeit> ohne Ergebnis“), `autopilot:wip` nehmen, `needs-human` setzen.
- Ein offenes Issue mit `autopilot:wip`, dessen PR mit Head `claude/autopilot-<n>` gemergt ist: `autopilot:wip` nehmen und das Issue schließen (`gh api -X PATCH repos/$REPO/issues/$N -f state=closed -f state_reason=completed`). Das schließt sonst der Review-Workflow; ist dort ein API-Aufruf gescheitert, räumst du nach, ohne es zu melden.
- Sonst änderst du keine Labels an Arbeit, die schon läuft. Antworten an `needs-human`-Fällen setzt der Mensch selbst per Label um; du nennst sie nur im Journal.

## 2b. Fragen beantworten

Je Frage aus dem Lagebild, vor jeder Kandidatensuche und ohne Deckel:

1. Spec, alle Kommentare und den Code dazu lesen; die Frage am Code beantworten, nicht aus dem Gedächtnis.
2. Kommentar mit `<!-- autopilot:antwort -->`: die Antwort in wenigen Sätzen, mit Pfaden, wo sie helfen.
3. Ändert die Antwort den Auftrag (Umfang, Akzeptanzkriterien, Klasse, Größe), zusätzlich einen Kommentar mit `<!-- autopilot:spec -->` mit der ganzen überarbeiteten Spec. Sie nimmt alle bisherigen Ergänzungen des Menschen auf, denn ältere Kommentare ohne Marker gelten danach nicht mehr. Wird daraus Klasse C, `autopilot:ready` oder `autopilot:proposed` nehmen, `needs-human` setzen und das in der Antwort sagen.
4. Lässt sich die Frage nur vom Menschen entscheiden, sagt die Antwort das und nennt die Optionen in einem Satz; die Spec bleibt.

Im Journal unter „Vorschläge zur Freigabe“ bekommt ein so beantwortetes Issue den Zusatz „Frage beantwortet“.

## 3. Platz für neue Aufträge

- **Klasse A** (`autopilot:ready`): nur, solange WIP plus wartende `autopilot:ready` unter dem WIP-Deckel liegen.
- **Klasse B** (`autopilot:proposed`): bis `deckel.offene_vorschlaege` minus der schon offenen Vorschläge. Ein voller WIP-Deckel sperrt Vorschläge nicht, sie belegen keinen Worker. Mit `freigabe_b: auto` gilt für Klasse B derselbe Platz wie für Klasse A, denn sie geht direkt auf `autopilot:ready`.
- Beides zusammen höchstens `deckel.neue_auftraege_pro_planerlauf` je Lauf.

Ohne Platz läuft der Doku-Sweep trotzdem, wenn er etwas zu tun hat (Inventur fällig oder Dokumente geändert): seine Ergebnisse gehen in den Vorrat. Issues und Bereichs-Review entfallen dann.

## 4. Kandidaten suchen

Die Quellen und ihre Reihenfolge stehen in `.claude/autopilot.md` unter „Planer-Quellen“. Arbeite alle Quellen ab, auch wenn die erste schon Kandidaten liefert, und wähle danach aus (Schritt 5). Für jede gilt:

- Übergehe Issues mit einem `autopilot:*`-Label, mit einem Ausschluss-Label, mit einem offenen PR auf `claude/autopilot-<n>`, und Issues aus der Liste „bewertet, nicht übernommen“, sofern sie seither nicht geändert wurden (`updated_at`).
- Vor jedem neuen Issue eine Dublettensuche über offene und geschlossene Issues. `search/issues` liefert im Cloud-Lauf 403: die Titelliste einmal je Lauf nach `/tmp/titel.txt` holen (Tabelle oben) und mit `grep -i -E '<Stichwort>|<Synonym>' /tmp/titel.txt` durchsuchen. Gibt es das Thema schon, kein neues Issue.
- Beim Bereichs-Review im Umlauf genau einen Bereich je Lauf ansehen, den nächsten nach „letzter Bereich“, und höchstens 2 Befunde daraus aufnehmen.
- Lies den Code, bevor du einen Befund behauptest. Ein Auftrag ohne geprüften Befund ist schlechter als keiner.

### Doku-Sweep (eigenes Repo und Zweit-Repos)

Der Sweep sieht in jedem Lauf den ganzen Doku-Bestand, nicht ein Dokument. Er liest nur Text, der Code-Abgleich kommt danach für eine begrenzte Auswahl.

1. **Umfang:** die Dokumente aus „Planer-Quellen“ in `.claude/autopilot.md` (Globs, Index-Tabellen, `§`-Einschränkungen), je Zweit-Repo dessen Liste. Pfade unter `archive/` und `archiv/` fallen heraus.
2. **Modus:**
   - **Inventur**, wenn das Gedächtnis keinen Sweep-Stand hat oder die letzte Inventur älter ist als `deckel.inventur_tage` (Vorgabe 30): der ganze Umfang.
   - **Änderungen** sonst: nur Dateien im Umfang, die sich seit dem Sweep-Stand geändert haben, je Repo `git log --name-only --format= <sha>..HEAD -- <pfade> | sort -u`. Ist der Klon flach (`git rev-parse --is-shallow-repository`), vorher `git fetch --shallow-since=<Datum des Sweep-Stands>`; fehlt der Stand-SHA danach immer noch, gilt der Lauf als Inventur.
3. **Treffer sammeln** mit einem `grep -n -i -E` über die Dateien des Modus: harte Marker (`- \[ \]`, Überschriften mit Offen, Nächste Schritte, Folge, Später, Idee, Entwurf, `TODO`, `FIXME`) und weiche (offen, später, noch nicht, fehlt, nicht gebaut, zurückgestellt, geplant, Folge-PR, Stufe 2, Phase 2). In Zweit-Repos nur Abschnitte, die `$REPO` nennen oder seine Pfade und Routen.
4. **Sichten:** Treffer je Abschnitt (nächste Überschrift darüber) bündeln, dann je Abschnitt den Text lesen. Weg fallen Abschnitte, die als erledigt markiert sind (✅, „erledigt“, „gebaut“, „umgesetzt“ mit Datum oder PR), reine Herleitung oder Messung ohne offene Arbeit, und alles, was schon im Vorrat, in „bewertet, nicht übernommen“ oder als Issue steht (Titelliste). Übrig bleibt eine Kandidatenliste: Abschnitt, offene Arbeit in einem Satz, vermutete Klasse.
5. **Am Code prüfen**, höchstens `deckel.pruefungen_pro_lauf` Kandidaten (Vorgabe 15), zuerst die mit harten Markern, dann Feature-Designs vor Subsystem-Doku vor Handbuch. Je Kandidat: `grep` nach den genannten Routen, Funktionen, Feldern, Env-Vars und Dateien in `$REPO`, `git log --oneline -i --grep=<Stichwort> | head` für eine schon gemergte Umsetzung. Steht das Werkzeug `Agent` zur Verfügung, prüfe in Gruppen von bis zu 5 Kandidaten parallel: jeder Subagent bekommt Abschnittstext, Repo-Pfad und die Einordnungsregel unten und antwortet mit Einordnung, geprüften Pfaden und einem Satz Befund. Ungeprüfte Kandidaten bleiben für den nächsten Lauf liegen; der Sweep-Stand rückt dann nicht vor, die Inventur gilt als nicht abgeschlossen.
6. **Einordnen:**
   - umgesetzt, aber die Doku sagt es nicht: Klasse A, Doku-Drift;
   - nicht umgesetzt, ohne offene Entscheidung, außerhalb der Sperrliste: Klasse B (oder A, wenn es nur Test, Lint oder Drift ist);
   - wartet auf eine Entscheidung, berührt die Sperrliste, braucht Hardware, prod oder ein anderes Repo: „bewertet, nicht übernommen“ mit Grund.
7. **Stand:** sind alle Kandidaten des Modus geprüft, Sweep-Stand je Repo auf `git rev-parse --short HEAD` und Datum setzen, bei Inventur auch deren Datum.

Geprüfte Kandidaten, die in diesem Lauf keinen Platz bekommen, kommen in den Vorrat. Der nächste Lauf nimmt den Vorrat zuerst (kurzer Gegencheck per `grep`, ob noch offen) und sweept danach.

## 5. Klassifizieren, auswählen und spezifizieren

**Klasse** nach `.claude/autopilot.md`:

- **C:** berührt die Sperrliste, auch nur am Rand, oder braucht eine Entscheidung aus „nie automatisch“. Kein Auftrag. Ein bestehendes Issue kommt mit Grund in „bewertet, nicht übernommen“.
- **A:** passt in eine Klasse-A-Kategorie und berührt die Sperrliste nicht.
- **B:** alles andere, was umsetzbar ist.

**Größe:** S (eine Stelle, unter 100 Zeilen), M (unter `deckel.diff_zeilen` Diff ohne Testdateien), L (mehr). L wird vorher in mehrere S/M-Aufträge geteilt; jeder Teil zählt gegen den Deckel. Ein Auftrag hat genau ein Ziel: zwei Teile, die einzeln nutzbar sind (etwa Oberfläche und Verwaltung), sind zwei Aufträge. Schätze nach Dateien und Schichten, nicht nach dem Gefühl; im Zweifel L.

**Auswahl** im Platz aus Schritt 3: Bugs mit Repro zuerst, dann Kandidaten aus Issues, dann der Vorrat, dann neue aus dem Sweep. Gibt es einen Klasse-B-Kandidaten und Platz für Klasse B, bekommt er mindestens einen der Plätze, auch wenn Klasse-A-Kandidaten alle füllen könnten. Einen umsetzbaren Klasse-B-Kandidaten hältst du nicht aus Vorsicht zurück: der Vorschlag kostet nichts, der Mensch entscheidet per Label. Was keinen Platz bekommt, geht in den Vorrat, nicht in „bewertet, nicht übernommen“.

**Spec-Gerüst** (Issue-Text bei neuen Issues, Kommentar bei bestehenden, beide mit Marker `<!-- autopilot:spec -->` in der ersten Zeile):

```
<!-- autopilot:spec -->
**Ziel:** ein Satz, was danach anders ist.
**Quelle:** Issue, Doku-Datei mit Abschnitt, oder `<owner>/<repo>:<pfad>` mit Abschnitt.
**Kontext:** Dateien mit Pfad, relevante Doku-Abschnitte, der geprüfte Code-Stand (was es schon gibt, was fehlt).
**Akzeptanzkriterien:**
- [ ] prüfbar
**Nicht-Ziele:** was ausdrücklich draußen bleibt.
**Tests und Doku:** welche Testdatei, welches Dokument im selben PR.
**Klasse und Größe:** A|B, S|M
**Zur Freigabe:** nur Klasse B mit `freigabe_b: mensch`, ein bis drei Sätze: Nutzen, offene Detailfrage, die der Mensch beim Freigeben beantworten kann. Mit `freigabe_b: auto` entfällt die Zeile; eine offene Detailfrage entscheidest du in der Spec selbst, und braucht sie wirklich den Menschen, ist der Auftrag nicht reif und bleibt im Vorrat.
```

Ein Worker, der dieses Repo nicht kennt, muss allein damit fertig werden. Jede Review-Runde kostet zwei Läufe, die Spec ist der größte Hebel.

**Label je Stufe:**

| Stufe | Klasse A | Klasse B |
|---|---|---|
| `trockenlauf` | `autopilot:proposed` | `autopilot:proposed` |
| `begleitet` | `autopilot:ready` | `autopilot:proposed` |
| `autonom` | `autopilot:ready` | `autopilot:proposed`, mit `freigabe_b: auto` `autopilot:ready` |

`autopilot:ready` an Klasse B setzt sonst nur der Mensch. Ohne `freigabe_b: auto` setzt du es dort nie, auch nicht an einem bestehenden Vorschlag. Mit `freigabe_b: auto` gibst du in Stufe `autonom` auch offene Vorschläge frei: `autopilot:proposed` nehmen, `autopilot:ready` setzen, im Rahmen des Platzes für Klasse A, die ältesten zuerst.

## 6. Journal fortschreiben (jeder Lauf, auch Leerlauf)

**Text des Journal-Issues ersetzen** (`PATCH`), Gerüst:

```
<!-- autopilot:journal-body -->
Stand: <Datum Zeit CET/CEST>, Stufe: <stufe>

### Braucht dich (needs-human)
- #n Titel: offene Frage in einem Satz (Antwort liegt vor: ja/nein)

### Vorschläge zur Freigabe (autopilot:proposed)
- #n Titel (Klasse, Größe)

### In Arbeit
- #n Titel: wip | review | changes Runde x

### Gemergt, letzte 7 Tage
- #pr Titel

### Heute
Worker-Läufe x, Planer-Läufe y (davon Nachschub z von <deckel>), WIP x von <deckel>, Budget: 5h x %, Woche y % (Soll z %)

### Planer-Gedächtnis
Sweep-Stand: <repo> <sha> <Datum>; <zweit-repo> <sha> <Datum>
Inventur: <Datum> (abgeschlossen | offen, n Kandidaten ungeprüft)
Letzter Bereich: <Zeile der Landkarte>
Vorrat:
- A|B S|M <Pfad> § <Abschnitt>: <Befund in einem Satz>
Bewertet, nicht übernommen: #n (Grund), <Pfad> § <Abschnitt> (Grund), …
```

Der Vorrat führt höchstens 30 Einträge, „bewertet, nicht übernommen“ höchstens 150 (ältere fallen vorne heraus). Der ganze Text bleibt unter 60 000 Zeichen; sonst zuerst die ältesten Einträge von „bewertet, nicht übernommen“ kürzen.
